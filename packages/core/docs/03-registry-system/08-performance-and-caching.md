# Performance and Caching

> **Registry commands in this guide** run in the NextSpark monorepo, from the repository root. In a generated project, build the registries with `pnpm build:registries` and watch them with `pnpm exec nextspark prepare --watch`.

## Overview

The Registry System removes runtime discovery: what used to be found by scanning the filesystem and reading config files at request time is generated by `nextspark prepare` as static modules, and runtime code only reads objects and calls loaders that were written into those modules. This document explains the mechanism, the caching model and the optimization practices. It states no timings: the repository has no benchmark that reproduces any, so none are claimed.

**Key properties:**
- ✅ No runtime filesystem I/O or discovery
- ✅ Direct object lookups by key
- ✅ Lookup cost does not depend on how many files the project has (the files are read at build time)
- ✅ Everything is reachable through static imports, so bundlers can trace and tree-shake it

## Performance Characteristics

### Zero Runtime I/O

Runtime discovery has to scan directories, read and process config files and build metadata on each cold start. The registries do that work once, in `prepare`:

```typescript
// ❌ Runtime discovery: filesystem work on the request path
async function getEntityRuntime(name: string) {
  const entityDir = await fs.readdir('./entities')
  const found = entityDir.find(dir => dir === name)
  const configModule = await import(`./entities/${name}/${name}.config.ts`)
  const config = await processConfig(configModule.starter)
  const migrations = await discoverMigrations(entityDir)
  const translations = await discoverTranslations(entityDir)
  return buildEntityMetadata(config, migrations, translations)
}

// ✅ Registry access: a property read on a static module
function getEntityRegistry(name: string) {
  return ENTITY_REGISTRY[name]
}
```

### Lookups are keyed, not scanned

A registry is a plain object keyed by slug, so a lookup is a property read. Iterating a registry (`Object.values(ENTITY_REGISTRY)`) visits every entry, as any iteration does.

### Memory

A registry holds the metadata that was computed at build time, plus static imports of the modules it references. Keep it to the metadata that is needed (see [Optimization Best Practices](#optimization-best-practices)).

## Caching Strategies

### Build-Time Generation

**Registry files ARE the cache**:

```typescript
// Registry = Pre-computed cache of all content
export const ENTITY_REGISTRY = {
  'tasks': { /* pre-discovered metadata */ },
  'projects': { /* pre-discovered metadata */ },
  'clients': { /* pre-discovered metadata */ }
}

// No runtime caching needed - already cached at build time
```

**Benefits:**
- Zero cache warming time
- No cache invalidation complexity
- No memory overhead for caching
- Cache is always "hot"

### Lazy Loading (Translations)

**Translation registry uses lazy loading**:

```typescript
// Lazy-load only active locale
export const THEME_TRANSLATION_LOADERS = {
  'starter': {
    'en': () => import('@/messages/en.json'),
    'es': () => import('@/messages/es.json'),
    'fr': () => import('@/messages/fr.json')
  }
}

// Only loads when called
const loader = THEME_TRANSLATION_LOADERS.starter.en
const translations = await loader()  // Loads only en.json

// Benefits:
// - Reduced initial bundle size
// - Faster page load
// - Lower memory usage
```

### Route Handlers

The generated host writes every project and plugin route as a route file of its own in `src/app`, so Next.js resolves each handler statically at build time and nothing imports a handler through a registry. The route-handlers registry keeps only the API route metadata the API Explorer reads (`API_ROUTES_METADATA`).

## When Registries Regenerate

### Development Mode

`nextspark dev` runs `prepare` once before Next starts (it fails fast if that generation fails), then watches the sources and regenerates `src/app` and the registries whenever they change. No restart is needed: the dev server serves the regenerated files. If a regeneration fails, the last valid output stays in place and the error shows in the terminal and in the browser.

```bash
pnpm dev
```

### Production Build

**Single generation** during build:

```bash
pnpm build
```

`nextspark build` runs `prepare` first, then the Next.js build, which uses the static registries. Nothing is regenerated at runtime: the registries are part of the production bundle.

### Manual Regeneration

**Force rebuild**:

```bash
cd apps/dev && node ../../packages/cli/dist/cli.js prepare
```

### Watch Mode

**Continuous regeneration** in development:

```bash
cd apps/dev && node ../../packages/cli/dist/cli.js prepare --watch
```

`nextspark dev` already does this for you; run `prepare --watch` on its own only when you want regeneration without starting Next.

## Cache Invalidation

### No Runtime Cache = No Invalidation

**Key insight:** Registries don't need cache invalidation:

```typescript
// Traditional runtime cache (needs invalidation)
class RuntimeCache {
  cache = new Map()
  
  async get(key: string) {
    if (this.cache.has(key)) {
      // Cache hit - but is it stale?
      const entry = this.cache.get(key)
      
      if (isStale(entry)) {
        // Cache invalidation needed
        this.cache.delete(key)
        const fresh = await fetchFromDisk(key)
        this.cache.set(key, fresh)
        return fresh
      }
      
      return entry
    }
    
    // Cache miss
    const data = await fetchFromDisk(key)
    this.cache.set(key, data)
    return data
  }
}

// Registry system (no invalidation needed)
const entity = ENTITY_REGISTRY.tasks  // Always valid, no staleness
```

### Build-Time Staleness

**Content changes require regeneration**, which `nextspark dev` does for you:

1. Edit `entities/tasks/tasks.config.ts`.
2. `nextspark dev` (or `nextspark prepare --watch`) regenerates the registries.
3. `ENTITY_REGISTRY.tasks` is up to date; no restart is needed.

In a production build, `nextspark build` regenerates them before Next compiles. There is no runtime invalidation logic.

## Performance at Scale

Generation cost grows with the amount of content, because `prepare` reads every entity, plugin, theme and translation once. Runtime access does not grow with it: a lookup is a property read on a static module, and only the registry entries a route imports reach that route's bundle. To see what your own project costs, time `nextspark prepare` and inspect the production build output; the repository ships no benchmark that turns this into a figure.

## Optimization Best Practices

### 1. Minimize Registry Size

**Keep registries lean**:

```typescript
// ✅ GOOD: Only essential metadata
export const ENTITY_REGISTRY = {
  'tasks': {
    slug: 'tasks',
    config: taskEntityConfig,
    hasComponents: false,
    hasMigrations: true,
    depth: 0
  }
}

// ❌ BAD: Unnecessary data bloat
export const ENTITY_REGISTRY = {
  'tasks': {
    // ... essential metadata ...
    fullFileContents: '...',      // Unnecessary
    allDependencies: [...],       // Unnecessary
    buildTimestamp: '...',        // Unnecessary
    developerComments: '...'      // Unnecessary
  }
}
```

### 2. Use Lazy Loading Where Appropriate

**Lazy load large data**:

```typescript
// ✅ GOOD: Lazy load translations
'en': () => import('@/messages/en.json')

// ❌ BAD: Import all translations upfront
import en from '@/messages/en.json'
import es from '@/messages/es.json'
import fr from '@/messages/fr.json'
// Bundle bloat!
```

### 3. Avoid Dynamic Imports

**Never bypass registries**:

```typescript
// ❌ BAD: Dynamic import (defeats entire system)
const entity = await import(`@/entities/${name}/config`)

// ✅ GOOD: Registry access
const entity = ENTITY_REGISTRY[name]
```

### 4. Cache Registry Lookups in Tight Loops

**Cache in hot paths**:

```typescript
// ❌ BAD: Repeated registry lookups
for (let i = 0; i < 1000; i++) {
  const entity = ENTITY_REGISTRY.tasks  // 1000 lookups
  doSomething(entity)
}

// ✅ GOOD: Cache the lookup
const entity = ENTITY_REGISTRY.tasks  // 1 lookup
for (let i = 0; i < 1000; i++) {
  doSomething(entity)
}
```

### 5. Leverage Tree-Shaking

**Import only what you need**:

```typescript
// ✅ GOOD: Named imports (tree-shakeable)
import { getEntity, getRegisteredEntities } from '@nextsparkjs/registries/entity-registry'

// ❌ BAD: Import entire registry
import * as EntityRegistry from '@nextsparkjs/registries/entity-registry'
```

## Monitoring and Profiling

### Performance Measurement

Measure in your own project rather than relying on published figures:

```typescript
import { performance } from 'perf_hooks'

const start = performance.now()
const entity = ENTITY_REGISTRY.tasks
console.log(`Registry access: ${(performance.now() - start).toFixed(4)}ms`)
```

### Build Performance Tracking

```bash
time pnpm exec nextspark prepare
```

The route-JS budget is tracked by `scripts/performance/verify-route-js-budget.mjs` (see `scripts/performance/README.md`).

## Troubleshooting Performance Issues

### Slow Registry Build

**Solutions:**
1. Check for large files in project source directories
2. Review filesystem performance
3. Reduce the number of entities/plugins temporarily to find the one that dominates

### High Memory Usage

**Solutions:**
1. Check for memory leaks in custom routes
2. Review plugin initialization hooks
3. Use a production build

### Registry Access Looks Slow

**Solutions:**
1. Verify you are using the registry, not dynamic imports
2. Check for heavy synchronous operations around the lookup
3. Profile with `performance.now()`
